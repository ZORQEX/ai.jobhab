# AI JobHub — поиск работы с AI-подбором

Веб-приложение на **Firebase Firestore + Firebase Authentication** и чистом
**Vanilla JavaScript (ES6-модули)** без сборщика. Каталог IT-вакансий, который
считает соответствие вакансии и резюме («подхожу на 82%»), объясняет оценку и
подсказывает, чего не хватает в резюме.

| | |
|---|---|
| **Демо** | https://ZORQEX.github.io/ai.jobhab/ |
| **Репозиторий** | https://github.com/ZORQEX/ai.jobhab |
| **Firebase-проект** | `ai-jobhub`, база в регионе `eur3` |
| **Схема БД** | [DATABASE.md](DATABASE.md) |
| **Правила безопасности** | [firestore.rules](firestore.rules) + [storage.rules](storage.rules) + тесты [tests/rules.test.js](tests/rules.test.js) |
| **Индексы** | [firestore.indexes.json](firestore.indexes.json) |

## Два режима работы

Приложение умеет работать с настоящим Firestore и без него:

* **Обычный режим** — Cloud Firestore и Firebase Authentication. Включается,
  когда в `src/config.js` заданы реальные ключи (они там уже есть).
* **Демо-режим** — то же приложение на localStorage браузера. Включается
  адресом `?demo=1`, например `index.html?demo=1`, и держится до закрытия
  вкладки. Нужен, чтобы показать приложение без сети, прогнать автотесты
  интерфейса и не расходовать квоту Firestore при отладке вёрстки.

Оба режима реализуют один и тот же контракт слоя данных, поэтому ведут себя
одинаково — включая подписки реального времени.

Демо-аккаунты (доступны в демо-режиме одной кнопкой на `auth.html`):

| Роль | Логин | Пароль |
|---|---|---|
| Администратор | `admin@jobhub.kz` | `admin123` |
| Соискатель | `user@jobhub.kz` | `user123` |

## Что реализовано

### Главная страница `index.html` (ТЗ 3.1)

* Каталог вакансий с пагинацией по 12 элементов, кнопка «Показать ещё»
  (курсорная, `startAfter` + `limit`, без `offset`).
* Поиск по названию, компании, описанию и навыкам — запросом к базе
  (`array-contains` по полю `searchTokens`) с доуточнением на клиенте.
* Фильтры: направление, город, грейд, занятость, «зарплата от», только удалёнка,
  плюс быстрые чипы. Состояние фильтров живёт в URL — ссылкой можно поделиться.
* Сортировка: по дате, по зарплате (в обе стороны), по числу откликов.
* **Real-time**: первая страница каталога — это `onSnapshot`. Новая вакансия
  появляется без перезагрузки, подсвечивается анимацией и сопровождается
  уведомлением «новая вакансия по вашему фильтру».
* Персональная AI-подборка «AI подобрал для вас» — три вакансии с наибольшим
  соответствием резюме и сводка недостающих навыков.

### Детальный просмотр `job.html` (ТЗ 3.2)

* Полное описание: обязанности, требования, «будет плюсом», условия, навыки
  (навыки, которые есть в резюме, подсвечены).
* **AI-анализ**: круговой индикатор «подхожу на N%», разбор по шести критериям
  с полосами, список недостающих навыков и конкретные рекомендации.
* Интерактив: отзывы о работодателе со звёздами, свой отзыв можно
  отредактировать или удалить. Новые отзывы прилетают через `onSnapshot`.
* Связанные элементы: похожие вакансии с пагинацией «Показать ещё похожие».
* Основное действие: «Откликнуться» (модалка с сопроводительным письмом и
  сохранением процента соответствия) и «Сохранить вакансию».
* **Real-time**: статус вакансии и счётчик откликов обновляются на лету — если
  админ закроет вакансию, кнопка отклика заблокируется сразу.
* Заголовок вкладки и Open Graph-теги подставляются из самой вакансии.

### Личный кабинет `profile.html` (ТЗ 3.3)

* История откликов со статусами в реальном времени и журналом смены статусов.
* Отзыв можно отредактировать или удалить во вкладке «Мои отзывы».
* Профиль: имя, телефон, город, о себе, тема оформления, уведомления.
* Фото профиля: загрузка в Firebase Storage с обрезкой и сжатием в браузере,
  замена и удаление; без фото показываются инициалы.
* Резюме для AI: должность, грейд, опыт, навыки (теговый редактор), желаемая
  зарплата, формат занятости, города, образование — плюс индикатор заполненности
  с подсказками, чего не хватает.

### Функциональная страница `saved.html` (ТЗ 3.4)

Сохранённые вакансии — аналог корзины: чекбоксы, личные заметки, удаление,
сортировка по соответствию и зарплате. Финализация — «Откликнуться (N)»:
на выбранные вакансии уходят отклики, элементы исчезают отсюда и появляются
в «Истории откликов».

### Админ-панель `admin.html` (ТЗ 3.5)

Доступ только для роли `admin` — гвард на клиенте и запрет в правилах Firestore.

* CRUD вакансий: создание, редактирование, открытие/закрытие, удаление.
* Логотип компании картинкой: загрузка в Firebase Storage, удаление — тогда
  в каталоге снова показывается эмодзи.
* Массовые действия: закрыть, открыть или удалить выбранные вакансии.
* Все отклики пользователей в реальном времени + смена статуса
  (`sent → viewed → interview → offer / rejected`) и выгрузка в CSV.
* Пользователи: список, назначение роли `user` / `admin`, блокировка.
* Модерация: скрыть или удалить любой отзыв.
* Статистика: агрегаты через `getCountFromServer()`, топ вакансий по откликам
  и график откликов по дням за последние 30 дней.

### Авторизация (ТЗ 3.6)

Регистрация, вход, выход, восстановление пароля письмом, сохранение сессии
(`browserLocalPersistence`), роли `user` (по умолчанию) и `admin`.

## Технологии

* Cloud Firestore — основная база данных.
* Firebase Authentication — email/пароль.
* Firebase Security Rules — разграничение доступа по ролям.
* Firebase Storage — аватары пользователей и логотипы компаний
  (правила в `storage.rules`, картинка уменьшается на клиенте до загрузки).
* Cloud Functions (папка `functions/`, требуют тарифа Blaze) — серверные
  счётчики, роль в custom claims, агрегаты, письма, генерация сопроводительных.
* Vanilla JavaScript (ES6-модули), HTML5, CSS3, адаптивная вёрстка от 360px,
  тёмная и светлая темы.
* В рантайме — ноль npm-зависимостей: Firebase SDK подключается динамическим
  `import()` с CDN. Всё в `package.json` — только инструменты разработки.

## Архитектура: один контракт, два хранилища

Страницы не содержат ни одного прямого вызова Firestore. Они работают с
объектом `backend`, который отдаёт `src/data/backend.js`:

```
pages/*.js  →  data/backend.js  →  firebase-backend.js  (ключи заданы)
                               ↘  demo-backend.js       (?demo=1 или нет ключей)
```

Оба адаптера реализуют одинаковый набор методов (`listJobs`, `watchFirstPage`,
`applyToJob`, `setApplicationStatus`, …), включая подписки: демо-адаптер
эмулирует `onSnapshot` через шину событий и событие `storage`, поэтому изменения
видны даже между вкладками.

Это правило проверяется автоматически: `tests/contract.test.js` сравнивает
наборы методов и число аргументов у обоих адаптеров, поэтому метод, добавленный
только в один из них, роняет тест, а не демо-режим на защите. Исключение ровно
одно и оно зафиксировано в тесте: `seedDatabase` (заливка данных в Firestore)
и `resetDemoData` (сброс localStorage) существуют только в своём режиме, и
админ-панель выбирает нужный по `backend.mode`.

## Как запустить локально

Нужен любой статический сервер — из-за ES-модулей открыть `index.html` как
файл нельзя. `npm run serve` поднимает свой на node: Python на машине может
быть не установлен, а node для линтера и тестов нужен всё равно. Подойдёт и
Live Server из VS Code, и `npx serve .`.

```bash
git clone https://github.com/ZORQEX/ai.jobhab.git
cd ai-jobhub
npm install                     # только инструменты разработки
npm run serve                   # статический сервер на node (tools/serve.js)
# открыть http://localhost:8080
```

## Проверки

```bash
npm install          # только инструменты разработки
npm run lint         # ESLint 9, flat config
npm run test:unit    # 30 тестов: движок подбора, компоненты, контракт адаптеров
npm run test:rules   # тесты правил Firestore на эмуляторе (нужна Java)
npm run test:storage-rules  # тесты правил Storage на эмуляторе (нужна Java)
npm run check:firebase      # диагностика живого проекта: правила, индексы, Storage
npm test             # всё сразу
```

`tests/rules.test.js` проверяет то, что нельзя проверить «на глаз»: что запрос
чужих откликов падает, что пользователь не может выдать себе роль `admin`,
переписать журнал статусов или накрутить счётчик откликов.
`tests/storage-rules.test.js` — то же для файлов: чужой аватар не
перезаписывается, логотип грузит только админ, не-картинка и файл больше 1 МБ
отбиваются, посторонние пути в бакете закрыты. На каждый push GitHub Actions
гоняет линтер и все наборы тестов (`.github/workflows/ci.yml`).

## Развёртывание Firebase

```bash
npm install -g firebase-tools
firebase login
firebase deploy --only firestore:rules,firestore:indexes,storage
```

`firebase.json` и `.firebaserc` уже в репозитории, поэтому `firebase init`
не нужен.

### Что нужно сделать в проекте один раз

Порядок важен: без индексов каталог отвечает `FAILED_PRECONDITION` и выглядит
пустым, а роль `admin` нужна, чтобы появилась кнопка заливки данных.

1. **Включить вход по email и паролю** — Console → Authentication → Sign-in
   method → Email/Password.
2. **Создать базу Firestore** в продакшен-режиме.
3. **Включить Storage** — Console → Storage → «Начать» (нужен для аватаров
   и логотипов; пока бакета нет, `--only storage` деплоить нечего).
4. **Залить правила и индексы:**
   ```bash
   npx firebase login
   npm run deploy:rules
   ```
   Индексов 45, сборка занимает несколько минут — в Console → Firestore →
   Индексы они должны перейти в состояние «Включён».
5. **Выдать себе роль администратора:** зарегистрироваться в приложении,
   затем в Console → Firestore у документа `users/{свой uid}` поменять
   `role` на `admin` и перезайти.
6. **Залить тестовые данные:** админ-панель → «Тестовые данные»
   (36 вакансий и 8 отзывов пачками через `writeBatch()`).
7. **Проверить результат:** `npm run check:firebase` — скрипт от лица гостя
   прогоняет по проекту все сочетания фильтров и сортировок каталога и
   показывает, где нет индекса, где мешают правила и пуста ли база.
   Все пункты должны быть отмечены ✔. Первый администратор назначается вручную: в Firestore у документа
`users/{ваш uid}` поле `role` меняется на `admin`; дальше роли выдаются из
админ-панели. Кнопка «Тестовые данные» в админке заливает 36 вакансий и отзывы
пачками через `writeBatch()`.

Cloud Functions (папка `functions/`) требуют тарифа Blaze и разворачиваются
отдельно: `cd functions && npm install && firebase deploy --only functions`.
Без них приложение полностью работоспособно.

## Как считается AI-соответствие

`src/ai/match.js` — детерминированный движок скоринга, тот же принцип, что у
ATS-систем при первичном отборе откликов. Внешняя языковая модель не
используется намеренно: оценка должна быть воспроизводимой, мгновенной для
каждой карточки каталога и не требовать серверного ключа.

| Критерий | Вес | Как считается |
|---|---:|---|
| Навыки | 45 | доля закрытых обязательных навыков + бонус за «будет плюсом» |
| Грейд | 18 | расстояние между грейдом резюме и вакансии; быть выше — мягче, чем ниже |
| Опыт | 12 | годы опыта против требуемых |
| Зарплата | 10 | попадают ли ожидания в вилку |
| Локация | 9 | город, удалёнка, режим «только удалённо» |
| Занятость | 6 | совпадение формата занятости |

Навыки сопоставляются по границам слов, а не по подстроке, плюс словарь
синонимов (`js → javascript`, `k8s → kubernetes`) и список пар-ловушек:
`javascript` не закрывает требование `java`, а `react` — `react native`.
Зато `react` закрывает `react hooks`. Всё это зафиксировано тестами.

Результат — процент, вердикт, разбор по критериям, список недостающих навыков
и текстовые рекомендации. Процент сохраняется в отклик
(`applications.matchScore`), поэтому его видит и админ в панели откликов.

Языковая модель подключается точечно и по желанию: callable-функция
`generateCoverLetter` в `functions/index.js` пишет сопроводительное письмо под
конкретную вакансию, а быстрый скоринг остаётся детерминированным.

## Оптимизация запросов

* **Денормализация.** В `applications` и `saved` лежит снимок вакансии
  (название, компания, вилка), поэтому история из 20 откликов — 1 запрос, а не 21.
* **Счётчики через `increment()`** вместо пересчёта: `applicationsCount`,
  `viewsCount`, `savesCount` у вакансии и `stats.*` у пользователя. Пишутся
  одной пачкой `writeBatch()` вместе с самим действием.
* **`getCountFromServer()`** в статистике — агрегаты считаются на сервере;
  с развёрнутыми функциями вместо них читается готовый `meta/stats`.
* **Офлайн-кэш** `persistentLocalCache` с `persistentMultipleTabManager`:
  повторное открытие каталога отдаётся из IndexedDB, а не новыми чтениями.
* **Курсорная пагинация** `startAfter(lastDoc)` + `limit()`.
* **Обозримый набор индексов вместо комбинаторного взрыва.** Пять фильтров и
  четыре сортировки дают 128 сочетаний, а лимит Firestore — 200 индексов на базу.
  Поэтому `planJobQuery` отправляет в запрос статус, ОДИН самый избирательный
  фильтр и сортировку (45 индексов на все случаи), а остальные условия отсеивает
  на клиенте. Покрытие всех сочетаний проверяет `tests/query-plan.test.js`.
* **Поисковый индекс** пишется при сохранении вакансии: `searchTokens`
  (≤ 40 токенов) для `array-contains`; в запрос уходит первый токен, остальные
  слова доуточняются на клиенте.
* **Дочитывание и запас.** Когда часть условий проверяется на клиенте,
  `listJobs` добирает следующую страницу курсором (до четырёх обращений), а
  снимок каталога берёт документы с четырёхкратным запасом и обрезает результат —
  иначе после отсева на странице осталось бы 2-3 карточки из 12.
* **`fieldOverrides`** в `firestore.indexes.json` отключают индексацию длинных
  текстовых полей, по которым никто не ищет.
* **Роль в custom claims** (Cloud Function `syncAdminClaim`): правила проверяют
  `request.auth.token.admin` и перестают делать `get()` на `users/{uid}` —
  минус одно чтение на каждый запрос. Пока функции не развёрнуты, правила
  автоматически откатываются на чтение документа.
* **О `select()`.** В веб-SDK Firestore проекции полей нет — это возможность
  серверных SDK. Эквивалент на вебе — та самая денормализация: в списках
  читаются лёгкие документы, а тяжёлый документ вакансии грузится только на
  её странице.

## Правила безопасности

Всё запрещено по умолчанию, доступ открывается точечно. Ключевая деталь: правило
запроса проверяется один раз против самого запроса, а не против каждого
документа выдачи, поэтому условие на `resource.data` заставляет клиента сузить
запрос — иначе весь запрос падает.

* вакансии читают все, но запрос обязан содержать `status == 'open'`; черновики
  и закрытые видит только админ; писать в вакансии может админ, а обычный
  пользователь — только счётчики и только шагом ±1;
* отклики: запрос обязан быть сужен по своему `userId`, иначе отказ — чужие
  сопроводительные письма и почты недоступны; создать можно только свой отклик
  со статусом `sent`, перевести — только в `withdrawn`, дописав ровно одну
  запись в журнал (переписать историю задним числом нельзя);
* отзывы: публичный запрос обязан содержать `hidden == false`, скрытые
  модератором доступны только админу;
* документ сохранённой вакансии проверяется и по полю `userId`, и по префиксу
  идентификатора `{uid}_{jobId}`;
* пользователь не может изменить собственные поля `role` и `disabled`.

Роль берётся из custom claim, который выставляет Cloud Function `syncAdminClaim`,
поэтому `isAdmin()` в правилах обходится без `get()` на `users/{uid}` — это
и платные чтения, и задержка на каждом документе выдачи. Пока функции не
развёрнуты, работает запасная ветка через `get()`.

### Файлы: `storage.rules`

Аватары и логотипы лежат в Firebase Storage, а не в документах Firestore.

* `avatars/{uid}/avatar.jpg` — писать может только сам пользователь, читать все;
  удалить может владелец или админ (на случай неподобающей картинки);
* `logos/{jobId}/logo.jpg` — писать только админ, по тому же custom claim;
* на запись стоит ограничение 1 МБ и `contentType: image/*`. Интерфейс и так
  уменьшает картинку до 256×256 (`src/core/image.js`, ~40 КБ), но правило
  страхует от загрузки оригинала в обход интерфейса;
* `delete` вынесен отдельной строкой: при удалении `request.resource` пуст,
  и проверка размера к нему неприменима.

В демо-режиме Storage не участвует: уменьшенная картинка сохраняется в
localStorage как data URL, а методы адаптера (`uploadAvatar`, `removeAvatar`,
`uploadCompanyLogo`, `removeCompanyLogo`) те же — контракт слоя данных
не расходится.
